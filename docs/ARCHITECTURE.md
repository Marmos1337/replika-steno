# Архитектура «Реплики»

Всё работает на телефоне. В манифесте нет разрешения INTERNET, поэтому приложение физически не может отправить аудио или текст наружу. Разрешения: микрофон (запись встречи) и то, что нужно живой записи, чтобы не обрываться при выключенном экране: фоновая служба типа «микрофон», уведомление о записи и удержание процессора (WAKE_LOCK).

## Конвейер

```
аудиофайл (SAF) ──────┐
микрофон (AAC) ───────┤
живая запись (WAV) ───┴─► filesDir/recordings/<id>/audio
                         │
                         ▼
1. Декодирование      MediaExtractor + MediaCodec → 16 кГц, моно, float
                         │
                         ▼
2. Диаризация         Silero VAD → фразы по паузам (длинные режутся каждые 12 с)
                      TitaNet-small → голосовой отпечаток (эмбеддинг) каждой фразы
                      кластеризация со средней связью по косинусному расстоянию, порог 0,6
                      → кто говорит когда; число говорящих не задаётся заранее
                      Segments.normalize: обрезка по длительности, склейка соседних фраз
                      одного говорящего (пауза < 600 мс), устранение наложений
                      speaker_1, speaker_2 … — по порядку первого появления
                         │
                         ▼
3. Распознавание      каждая реплика отдельно (длинные режутся в самой тихой точке, ≤ 20 с)
                      GigaAM v3 (русский, с пунктуацией) → если ответ в основном латиницей,
                      та же фраза распознаётся Parakeet TDT-CTC 110M (английский)
                         │
                         ▼
4. Оформление (LLM)   Qwen2.5-0.5B-Instruct, MediaPipe LLM Inference, жадное декодирование
                      получает только текст реплик пачками по 6 строк;
                      TextGuard принимает ответ, только если последовательность слов
                      совпадает с исходной (меняться могут лишь пунктуация и регистр)
                         │
                         ▼
5. Итоги              та же LLM, окна по ~1200 символов с глобальной нумерацией реплик,
                      пример ответа в промпте; разделы «Кратко», «Решения», «Вопросы»,
                      «Поручения» (что / кто / срок). Пункт должен опираться на слова
                      процитированных реплик, иначе отбрасывается; если модель не дала
                      номер, ссылка ставится на реплику с теми же словами; «кто» и «срок»
                      остаются, только если эти слова сказаны в процитированной реплике
                         │
                         ▼
   Recording (JSON в filesDir) → экран расшифровки → экспорт по схеме организаторов
```

Границы времени и speaker_id задаёт только диаризация (шаг 2). LLM не видит времени и говорящих при оформлении и не может их изменить. Исходный текст распознавателя хранится в `Utterance.rawText` и не меняется ни LLM, ни ручной правкой пользователя.

## Экспорт

`TranscriptJson.encode` пишет ровно ключи `speaker_id`, `start_ms`, `end_ms`, `text`, время — целые миллисекунды. Отображаемые имена участников лежат отдельно в `Recording.speakerNames` и в экспорт не попадают. Перед экспортом `TranscriptJson.validate` проверяет `0 <= start_ms < end_ms <= длительность` и формат `speaker_N`.

## Уверенность

Распознаватели в sherpa-onnx не отдают оценку уверенности по словам, поэтому процентов «точности распознавания» приложение не показывает. Настоящая оценка есть у диаризации: косинусная близость голосового отпечатка фразы к центру её кластера (от −1 до 1). Реплики с близостью ниже 0,5 помечаются «говорящий под вопросом».

## Модули

| Пакет | Что внутри |
|---|---|
| `core` | модель данных, декодер аудио, сегменты, `Pipeline`, `TextGuard`, `SummaryParser` |
| `diar` | `VadDiarizer` (sherpa-onnx VAD + эмбеддинги), `Clustering` (чистый Kotlin) |
| `asr` | `SherpaRecognizer` (GigaAM + Parakeet), `ModelAssets` |
| `llm` | `LlmFormatter` (MediaPipe + Qwen) |
| `data` | `RecordingStore` (файлы JSON), `Settings` (DataStore + синхронное зеркало темы) |
| `export` | `TranscriptJson` |
| `ui` | Jetpack Compose: записи, обработка, расшифровка, итоги, «О приложении» |

Шаги 1–3 — первая фаза: как только распознавание готово, запись получает статус «Готово» и расшифровка открывается. Шаги 4–5 идут второй фазой в фоне (`llmPending`), правки пользователя за это время не затираются. После обработки LLM закрывается сразу, модели распознавания — через 30 с простоя (память процесса падает с ~1,5 ГБ до ~150 МБ).

Обработка идёт в корутине уровня приложения: уход с экрана её не прерывает, «Отменить» останавливает её между фразами (и между пачками LLM). Если процесс был убит во время обработки, при следующем запуске новая запись помечается «Остановлено», а у повторной обработки остаётся прежняя расшифровка. Сохранение статуса после отмены выполняется в `NonCancellable`, чтобы отмена не отменила и саму запись статуса.

## Почему не pyannote

Сначала стояла связка pyannote-segmentation-3.0 + CAM++ из sherpa-onnx. На тестовых диалогах она склеивала соседние реплики разных людей через паузу < 1 с и ошибалась в 3–4 репликах из 8. Схема «VAD → TitaNet-small → своя кластеризация» на тех же файлах дала 8 из 8 и 4 из 4 правильных говорящих, причём одинаково на порогах 0,5–0,7. Подробности в `docs/TEST_RESULTS.md`.

## Живая запись

Текст появляется во время разговора. Новых моделей нет: те же GigaAM v3 / Parakeet, Silero VAD и TitaNet-small работают в режиме «псевдопотока».

```
AudioRecord 16 кГц PCM16, блоки по 100 мс (свой поток, приоритет аудио)
   │
   ├─► WAV в filesDir/recordings/<id>/audio — пишется сразу, это главный источник
   │
   └─► очередь (не больше 30 с звука) ─► один рабочий поток «live-asr»
            Silero VAD (свой экземпляр, пауза 0,3 с, фраза ≤ 10 с)
            ├─ фраза закрылась → распознаётся один раз → подтверждённая строка
            │   (+ до 300 мс звука до начала, но не больше половины паузы до прошлой строки)
            ├─ фраза ещё идёт → раз в 600 мс распознаётся её начало → предварительный текст,
            │   заменяет прошлый; когда приходит подтверждённая строка, он исчезает
            └─ TitaNet по фразам ≥ 1 с → «Голос N» (онлайн-кластеры, порог 0,6) — только подсказка
```

- Строки не повторяются и не теряются: каждая фраза VAD распознаётся ровно один раз, интервалы строк не пересекаются.
- Захват никогда не ждёт модель. Если в очереди есть звук, предварительный текст пропускается: на медленном телефоне время уходит на подтверждённые строки. Отставание (`backlogMs`) видно в состоянии; больше 4 с — показывается предупреждение. Если отставание дошло до 30 с, живой текст пропускает кусок, но звук уже на диске и попадёт в итоговую расшифровку.
- Память ограничена: в памяти только последние 30 с звука, очередь до 30 с и последние 5000 замеров задержки.
- Пауза останавливает AudioRecord (индикатор микрофона гаснет) и закрывает текущую фразу. Время на паузе в запись не входит.
- «Стоп»: доразбираются фразы из очереди, WAV закрывается, запись уходит в обычный конвейер (диаризация заново, распознавание, LLM). Итоговая расшифровка и JSON те же, что для импорта. Живой текст хранится в `Recording.liveDraft` как черновик и никогда не экспортируется.
- Если приложение убили во время записи, при следующем запуске заголовок WAV чинится по фактическому размеру, а запись появляется со статусом «Остановлено» и кнопкой «Обработать снова». Обрывки короче 1 с удаляются.
- Запись держит фоновая служба `LiveRecordingService` (тип microphone) с уведомлением «Идёт запись · 03:12» и кнопками «Пауза» / «Стоп».
- Пока идёт живая запись, новые импорты ждут в очереди. Уже запущенная обработка доходит до конца; распознаватель общий, поэтому живой текст в это время может отставать (это видно по предупреждению).
- Предел — 2,5 часа, как у импорта: потом запись останавливается сама.

### Замеры

При остановке в logcat пишется одна строка `LIVE_METRICS {json}` (тег `Replika`), те же числа сохраняются в `Recording.liveMetrics`: время до первого текста, задержка обновления (медиана и p95: момент показа текста минус момент записи последнего звука, вошедшего в распознавание), RTF распознавания, скорость обработки потока (`speedX`, во сколько раз быстрее реального времени), максимальное отставание и длина очереди, пик PSS, число предварительных/подтверждённых/пропущенных обновлений и пропущенный звук.

### Прогон из файла (только отладочная сборка)

Файл проигрывается в живой движок в реальном темпе вместо микрофона. В сборке без `debuggable` параметр игнорируется.

```bash
adb push testdata/long_live_16min.m4a /sdcard/Android/data/ru.replika.steno/files/live.m4a
adb shell pm grant ru.replika.steno android.permission.RECORD_AUDIO   # для фоновой службы при выключенном экране
adb shell am start -n ru.replika.steno/.MainActivity --es live_test_file live.m4a
adb logcat -s Replika:I | grep LIVE_METRICS
```

Имя без пути ищется в `/sdcard/Android/data/ru.replika.steno/files/`, абсолютный путь берётся как есть (файл должен быть доступен приложению). Когда файл закончится, запись останавливается сама и уходит в обычную обработку.
